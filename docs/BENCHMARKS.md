# Measured performance

Run it yourself:

```bash
npm run bench
```

The script is `scripts/bench-pipeline.mjs`. It exits non-zero if the free path
regresses past the product target, so it is a real check, not a report.

## What this measures

Only the stages that run on this machine **with no credentials and no real
audio**. Nothing here is an estimate or a vendor claim.

| Stage | Measured |
|---|---|
| `matchFastPath` (local reply library) | **p50 0.049 ms, p95 0.082 ms, max 1.66 ms** |
| `detectMaterialChange` (material-change check) | p50 0.018 ms, p95 0.031 ms |
| `decideProvisional` (trigger decision) | p50 0.012 ms, p95 0.031 ms |

Measured on the development laptop, Node 24, 2000 iterations per row after a
200-iteration warm-up. These are per-call microbenchmarks of pure functions, so
they are stable, but they say nothing about network or model speed.

## The number that matters for the requirement

`prompt_2.txt` §8 asks for a useful provisional suggestion within roughly **1
second** of sufficient partial context existing.

When the library matches, reply generation takes **p95 0.082 ms**. The 1-second
budget is therefore entirely consumed by things this script cannot measure —
transport and the speech recogniser — not by reply generation. That distinction
is the honest one: a fast reply engine cannot make a slow recogniser fast.

## Library coverage

On the script's eight synthetic partials, **8/8** matched, and each routed to the
correct category after the routing bugs below were fixed:

| Partial | Category |
|---|---|
| "Could you explain why the application is taking longer to" | `acknowledge-question` |
| "…move the deadline to Friday" | `negotiate-deadline` |
| "I am not sure what you mean by that exactly" | `ask-clarification` |
| "Can you confirm the next step and who is picking it up" | `confirm-next-step` |
| "The audio is breaking up a little on my side" | `ask-repeat` |
| "We also need to add reporting to the same sprint" | `out-of-scope` |

Two real bugs the benchmark caught in the first run, both now fixed:

1. A single-word cue ("deadline") could never reach the score-2 threshold, so
   genuinely relevant sentences matched nothing. Added multi-word phrase cues.
2. "can you confirm the next step…" mis-routed to `express-uncertainty`, because
   "can you confirm" was a cue there and ties break to the earlier record.
   Removed that ambiguous cue from the uncertainty record.

This is why the benchmark runs the real matcher instead of asserting a constant.

## The full local pipeline, on real speech (`npm run bench:local`)

The microbenchmarks above measure pure functions. This one measures the whole
₹0 path with a real recogniser and a real recording:

```
PASS  local recogniser present: .local-models/Release/whisper-cli.exe
PASS  local model present:       .local-models/ggml-base.en.bin
PASS  test speech loaded:        .local-models/test-speech.wav (143246 bytes of real audio)
PASS  transcript (2870 ms): "Can you explain why the application is taking longer to load today?"
PASS  reported mode "chunked" (chunked, not streaming - stated honestly)
PASS  transcript contains the words that were actually spoken
PASS  suggestion (2.020 ms): "Let me check that and come back to you."
PASS  matched category "acknowledge-question", engine "local_library"
PASS  provisional reply does not assert an unknown fact

  speech -> transcript : 2870 ms  (local Whisper, ggml-base.en.bin)
  transcript -> reply  : 2.020 ms  (local library)
  speech -> suggestion : 2872 ms
```

| Stage | Measured | Share of the 1 s target |
|---|---|---|
| speech → transcript (local Whisper) | **2870 ms** | over budget |
| transcript → suggestion (local library) | **2.020 ms** | 0.2% |

**This does not meet the `prompt_2.txt` §8 target of ~1 s, and the reply engine
is not the reason.** 2 ms of the 2872 ms is reply generation. The cost is
`whisper-cli` starting a fresh process per chunk plus CPU inference on
`base.en`. Options to close the gap (neither implemented) are a smaller model or
`whisper-server.exe` keeping the model resident — `docs/LOCAL_STT.md`.

The audio is a Windows SAPI TTS sentence generated by
`scripts/make-test-speech.ps1`; the transcript is verbatim correct against what
was spoken. It is real audio through a real recogniser, not a fixture string.
This route is **chunked** — there are no interim partials, so text appears when
a chunk closes, and the provisional reply cannot fire mid-sentence from
transcript text alone.

## Local STT transports: process-per-chunk vs resident model (`npm run bench:stt`)

Same audio, same model, both transports, 5 iterations after a warm-up:

```text
cli    (process per chunk)  min 3705  p50 3868  p95 4057  max 4057 ms
server (resident model)     min 2819  p50 2921  p95 2985  max 2985 ms

p50 improvement: 1.32x (946 ms saved per chunk)
```

| Transport | p50 per chunk | What it pays for |
|---|---|---|
| `cli` (`whisper-cli.exe`) | **3868 ms** | process start + model load + inference |
| `server` (`whisper-server.exe`) | **2921 ms** | inference only |

Both returned the identical transcript, so the faster path does not trade
accuracy for speed. The ~950 ms gap is exactly the per-chunk startup that server
mode removes; the remaining ~2.9 s is CPU inference on `base.en`, which server
mode cannot reduce. Closing that needs a smaller model or faster hardware.

Honest caveat: these numbers move with machine load. An earlier run measured
2870 ms for the CLI path. This box runs near its 16 GB commit ceiling
(`COVEXCODE.md`). Both figures are real; neither is an estimate.

Roughly, the text lags the speaker by `chunk (2400 ms) + transport`:
~6.3 s on `cli`, ~5.3 s on `server`. That is why the local route is honest about
being chunked rather than claiming to meet the ~1 s provisional target.
## Model accuracy: `tiny.en` vs `base.en` (`npm run bench:models`)

10 synthetic sentences with known ground truth, scored by real word error rate
(Levenshtein alignment after normalisation), in two conditions.

| Model | Clean: exact | Clean: WER | Noisy 10 dB: exact | Noisy 10 dB: WER | p50 ms |
|---|---|---|---|---|---|
| `ggml-tiny.en.bin` | **10/10** | 0.0% | 9/10 | **1.5%** | 1097–1616 |
| `ggml-base.en.bin` | **10/10** | 0.0% | 10/10 | **0.0%** | 2811–4477 |

The single `tiny.en` error at 10 dB SNR:

```text
said: "I will check with the backend team and get back to you tomorrow"
got : "I will check with the back in team and get back to you tomorrow."
```

That is the dangerous shape of a small-model error: one wrong word inside an
otherwise fluent sentence. It is not gibberish, so it would not look broken in the
UI — it would read as a fact. `base.en` got it right.

**Speed vs accuracy trade-off:** `tiny.en` saves 1.7–4.1× of latency for accuracy
that is identical on clean speech and marginally worse under noise. On a 10-sentence
sample, one word is not statistically meaningful, so this is "close, slightly worse
under noise" — not "1.5% worse".

**Measurement fixes worth recording.** The first version of this benchmark reported
both models at 1.5% WER, because it scored `backend` vs `back-end` as an error.
Hyphens are now stripped rather than turned into a space. It also could not tell the
models apart at all on clean speech, which is why the noisy condition exists.

**Variance caveat.** Two runs disagreed on absolute latency (`base.en` p50 4477 vs
2811 ms) and a third run was killed after 300 s without completing a condition.
This laptop sits near its 16 GB commit ceiling (`COVEXCODE.md`). Treat the ratio as
a range and re-measure before quoting a single number.

## What is NOT measured here — and cannot be, without credentials

- capture start → first audio frame
- first audio frame → first partial transcript
- partial transcript → provisional suggestion, end to end
- LLM request → first token / completed reply
- finalised transcript → refined reply
- end-to-end speech → suggestion

These need either `OPENAI_API_KEY` (the WebRTC realtime path) or `STT_API_KEY`
(the chunked path), **plus a real meeting tab producing speech**. No credential
exists in this environment, so no end-to-end latency figure is claimed anywhere
in this repository.

To measure them once a key exists, the app already records per-reply timings and
the UI shows `Speech → reply`, `Speech → text`, `Text → request` and
`Request → reply`. Report those actual numbers rather than expectations.

Only `openai-realtime` (WebRTC) produces genuine interim partials. The chunked
and local routes finalise per chunk by design — `docs/STT_PROVIDERS.md`.

## Server-side stage timing already instrumented

Cheap, content-free timing that is safe to log:

| Event | Fields | Where |
|---|---|---|
| `reply.fast_path_hit` | `record`, `score`, `ms` | `replyEngine.ts` |
| `stt.chunk` | `seq`, `bytes`, `providerMs`, `chars` | `routes/stt.ts` |
| `realtime.token_issued` | `model`, `ms`, `ttlSeconds` | `realtimeTokens.ts` |

`chars` is a length, never the text. No transcript content is logged.
